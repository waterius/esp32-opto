# Миграция настроек: ничего не теряется при обновлении

План от 2026-09-20. Ветка `reliability`.

## Контекст

Сейчас настройки лежат в NVS одним бинарным блобом `core::Settings` (336 байт,
namespace `opto`, ключ `settings`). `storage::loadSettings()`
(`src/port/storage.cpp:47`) отвергает запись **дважды**: `loadBlob()` сверяет
длину (`getBytesLength(key) == sizeof`), а затем сверяется
`stored.version == SETTINGS_VERSION`. Любое несовпадение → `s = core::Settings()`,
полный сброс: устройство уходит в точку доступа и настраивается заново.

Из этого следует, что **новое поле в структуре роняет настройки даже без подъёма
версии** — просто потому, что изменился `sizeof`. Так и произошло в 71b5459
(«SETTINGS_VERSION не поднят: размер блоба storage сверяет отдельно»). А в
dcda09b версию подняли ради одной строки — смены хоста облака по умолчанию, — и
ценой этого стал сброс ключа облака, пароля Wi-Fi и всех тарифных кодов на уже
настроенных платах.

Цель: обновление прошивки не должно стоить ни одной настройки. Добавление поля —
бесплатно; изменение смысла поля — по функции апгрейда на версию.

Прецедент против наивной цепочки: waterius живёт на `VER_11`
(`~/CODE/waterius/ESP8266/src/core/types.h:26`) и конвертеров не написал ни
одного — `load_config()` (`config.cpp:140-185`) при несовпадении версии делает
`init_config()` и спасает руками два поля, причём одно ещё и проверяет на
разумность, «потому что в конфиге прошлой версии по этому смещению мог оказаться
совсем другой байт». Одиннадцать версий — и цепочку никто не потянул. Поэтому
цепочка здесь строится так, чтобы её звенья появлялись редко и были короткими.

## Решение

Цепочка апгрейдов сохраняется ровно в задуманном виде (версия в памяти, функция
на версию, `v3 → v4 → v5`, результат сразу сохраняется), но носителем записи
становится **JSON через ArduinoJson**. ArduinoJson 7.3.1 уже в `lib_deps` обоих
env, включая `native` (`platformio.ini:26, 66`), и `core/cloud.cpp` на нём уже
собирает тело запроса в облако — правило «внешние библиотеки вместо своих
реализаций» соблюдено.

Что это даёт: разбор начинается с `core::Settings{}` и перекрывает **только те
ключи, что есть в записи**. Новое поле берёт умолчание само, удалённое молча
игнорируется, версия при этом не двигается. Функции апгрейда пишутся только на
смысловые правки и содержат разницу, а не перекладывание 25 полей руками — то
есть в них нет места для молчаливого пропуска поля.

Правило версии меняется на:

> `SETTINGS_VERSION` поднимается, только когда меняется **смысл** уже
> существующего поля: единицы, интерпретация, имя, разделение на два. Добавление
> и удаление поля версию не двигают. На каждый подъём — функция
> `upgradeNtoN+1(JsonObject)` и тест на неё.

### Три пути чтения

| Что в NVS | Что делаем |
|---|---|
| ключ `cfg` (JSON) | разобрать поверх умолчаний → прогнать цепочку от `v` до текущей → если цепочка что-то сделала, сразу сохранить |
| ключа `cfg` нет, есть `settings` (блоб v4, 336 байт) | разовый перенос: прочитать замороженной раскладкой → **записать `cfg` и убедиться, что запись прошла** → только потом удалить `settings` |
| ни того, ни другого, либо запись не разбирается | умолчания, строка в лог |

Запись версии **из будущего** (откат прошивки, `v` больше текущей): цепочка не
запускается, читаются известные ключи, неизвестные пропускаются, в лог —
предупреждение. Wi-Fi и ключ облака при откате выживают.

Ключ `fast` (канал и BSSID, 7 байт, без версии) остаётся как есть и по-прежнему
накладывается поверх после загрузки (`storage.cpp:54-58`). В JSON `bssid` и
`channel` тоже пишутся — как и сегодня в блобе; `fast` просто выигрывает.

Ключ `reading` (последнее показание) **не трогаем**: это кэш, не сошлась запись —
показания перечитаются со счётчика на ближайшем цикле опроса. Решение осознанное,
записать в docs.

## Файлы

**Новое ядро:**

- `src/core/settings_io.h` / `src/core/settings_io.cpp` — сериализация, разбор,
  цепочка апгрейдов.

  ```cpp
  namespace core {
  enum class LoadResult { Ok, Migrated, FromFuture, Defaults };

  // Возвращает длину записи; 0 — не поместилось в cap (запись не менять!).
  size_t settingsToJson(const Settings& s, char* out, size_t cap);

  // Стартует с умолчаний, перекрывает только присутствующие ключи,
  // затем поднимает версию цепочкой.
  ```

```sh

~/.platformio/penv/bin/pio run -e esp32-s3 -e esp32-c3     # static_assert раскладки v4 — здесь
```

Код возврата смотреть у самого `pio`, без `grep`/`tail` после него. Сборка под
платы важна отдельно от тестов: `static_assert` на `sizeof`/`offsetof` проверяет
раскладку на xtensa и riscv32, а не только на x86-64 хоста.

На плате (C3 — проверить чип по MAC перед заливкой, на столе есть посторонний C6):

1. Залить **текущую** прошивку, настроить через точку доступа: Wi-Fi, ключ
   облака, период, тарифные коды.
2. Залить новую прошивку (`-t upload`, раздел NVS при этом не стирается).
3. `pio device monitor`: в логе должно быть «настройки перенесены из формата 4»,
   страница настроек показывает всё ровно как до обновления, устройство само
   подключается к Wi-Fi и уходит в облако.
4. Перезагрузить ещё раз: переноса больше нет, читается `cfg`.

Без платы: `python3 tools/fake_device.py` — проверить, что `/api/settings` отдаёт
и принимает то же, что и раньше (словарь ключей не менялся).

## Как вышло

Реализовано в `bcba409` (PR #7). Два отступления от плана:

- **буфер записи 1536, а не 1024.** Предельные настройки (все строки
  максимальной длины из сплошных кавычек — худший случай экранирования)
  занимают 971 байт. Запаса до 1024 оставалось 53 байта, а цена переполнения —
  «настройки не сохраняются вообще»;
- **поле `core::Settings::version` убрано.** После перехода на JSON его не
  читал никто: версия живёт в ключе `v`. Заодно проверка самой схемы — структура
  поменяла размер, и ничего не упало.

Замороженная раскладка оправдалась сразу: `static_assert` поймал пропущенный
хвостовой байт-заполнитель `SerialCfg` (`meterEnabled` уезжал на 135 вместо
136). Без них перенос читал бы чужие байты — а число 336 при этом сходилось.

Адреса (`ip`, `gateway`, `mask`, `dns`) в записи лежат числами, а не точечной
записью: разбирать её ядру нечем (`IPAddress` — это Arduino), а запись в NVS
человек не читает. На странице они по-прежнему точечные.
