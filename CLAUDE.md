This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Язык проекта — русский: документация, комментарии, сообщения коммитов

## Сборка

PlatformIO Core 6.2 лежит в `~/.platformio/penv/bin/pio` и **в PATH не
добавлен**, поэтому вызывать его нужно по полному пути. `idf.py` не
установлен.

```sh
~/.platformio/penv/bin/pio run -e esp32-s3 -e esp32-c3   # сборка обеих плат
~/.platformio/penv/bin/pio run -e esp32-s3 -t upload     # прошивка
~/.platformio/penv/bin/pio run -e esp32-s3 -t uploadfs   # веб-страницы из data/
~/.platformio/penv/bin/pio test -e native                # юнит-тесты, без платы
~/.platformio/penv/bin/pio device monitor                # лог, 115200
python3 tools/fake_cloud.py                              # заглушка облака Waterius
python3 tools/fake_device.py                             # веб-страницы и API без платы
```

Юнит-тесты есть только у протокола обмена со счётчиком: `test/test_nartis`
гоняет `NartisMeter` через байты оптопорта — на эмуляторе счётчика и на
реальном дампе (`docs/06-nartis-100-exchange.md`). Env `native` собирает из
`src` только протокол (`build_src_filter`). Тесты не лезут внутрь Gurux,
поэтому при смене реализации меняется лишь `readMeter()` в тесте.

Пины оптопорта задаются флагами `OPTO_RX_PIN` / `OPTO_TX_PIN` в
`platformio.ini`, отдельно для каждого env. У C3 два обязательных отличия:
раздел `min_spiffs.csv` (в `default.csv` приложение не влезает, а OTA нужен)
и `-DARDUINO_USB_MODE=1` (без него `Serial` не объявлен).

При проверке сборки смотреть код возврата самого `pio`: если после него в
конвейере стоит `grep` или `tail`, код возврата будет от них.

**Утверждённый дизайн — `docs/superpowers/specs/2026-09-17-esp32-opto-firmware-design.md`.**
Код приводится к нему; при расхождении прав дизайн. Правило проекта —
внешние библиотеки вместо своих реализаций (Gurux, ESPAsyncWebServer,
ElegantOTA, igrr/rfc2217-server), портал Wi-Fi переносится из waterius.

## Структура

```
src/core/     ядро, без Arduino: nartis (адаптер на GuruxDLMS.c), cloud (запрос
              в облако, разбор ota), settings.h, meter.h, opto_port.h
src/port/     железо: opto_bus (владелец UART1), opto_esp32, net (Wi-Fi, HTTPS),
              wifi_portal (перенос из waterius), web (API), rfc2217, ota_cloud,
              storage (NVS), log (USB + кольцевой буфер), hal_esp32
src/poller.*  автомат опроса счётчика и отправки в облако
src/app.h     общее состояние и флаги запросов с веб-страниц
data/         четыре страницы, app.js, style.css — образ LittleFS
lib/rfc2217-server/  копия igrr/rfc2217-server с патчем (см. PATCHES.md)
test/test_nartis/    юнит-тесты протокола: эмулятор счётчика и реальный дамп
tools/        nartis_probe.py — опрос счётчика с компьютера, fake_cloud.py —
              заглушка облака для проверки отправки и OTA, fake_device.py —
              симулятор устройства: страницы из data/ и API прошивки без платы,
              значения счётчика задаются на его странице /sim
docs/         исследование ИК-головки RIXUTECH на CP2102N и её доработки
```

Ядро не включает заголовки Arduino: время оно берёт через `core::nowMs()` /
`core::sleepMs()`, порт — через `core::IOptoPort`. Реализации обеих
абстракций живут в `src/port/`. При добавлении второго счётчика он
наследует `core::IMeter` рядом с `NartisMeter`.

**Правило потоков.** Весь наш код работает в `loop()`. Веб-хендлеры (задача
`async_tcp`) и колбэки сервера RFC 2217 (его задачи) только читают `app` и
ставят атомарные флаги; UART, NVS, TLS и переключения Wi-Fi — только из
`loop()`. При любом изменении `core::Settings` поднять `SETTINGS_VERSION`.
Вывод — только через `Log` (`src/port/log.h`), не `Serial`: иначе сообщения
нет на странице лога.

Документы в `docs/` описывают ESP32-C6 (UART1, GPIO18 = TX, GPIO19 = RX) —
это осталось от исследования головки, сборка сейчас под S3 и C3.

### Правило для docs/

Каждое утверждение в документах помечается уровнем достоверности:
**[проверено]** (со ссылкой в `docs/sources.md`), **[по схеме]**,
**[по фото]**, **[гипотеза]**, **[измерить]**. Новые документы
нумеруются дальше (`06-…md`) и добавляются в таблицу `docs/README.md`.

## Цель: прошивка для электросчётчика НАРТИС

Что нужно (со слов владельца):

- Целевой чип — **ESP32-S3**. Поддержка **ESP32-C3** обязательна.
  Документы про C6 остаются справкой по головке.
- **Порт отделён от ядра.** Ядро — платформонезависимый C++: протокол
  счётчика, планировщик, сбор данных для облака, модель настроек. Порт —
  всё железо и ОС: serial-транспорт, Wi-Fi, NVS, HTTP-клиент,
  веб-сервер, сокеты, время. Ядро не включает заголовки ESP-IDF/Arduino.
- Протокол счётчика реализует **отдельный класс-адаптер**. Поддерживается
  только НАРТИС, но адаптер работает с ядром через интерфейс.
- Плата всегда подключена к питанию и Wi-Fi. Глубокого сна нет (в отличие
  от основной прошивки Waterius, где ESP будит Attiny).
- **Arduino через PlatformIO**, похоже на прошивку Waterius, но сильно
  проще: проект не для production, упрощать можно по максимуму. Прозрачный
  serial — по **RFC 2217**, чтобы порт открывался обычными программами
  через виртуальный COM.
- **Режим «прозрачный serial»**: удалённо слать и читать байты оптопорта и
  менять параметры COM-порта (скорость, биты, чётность, стоп-биты). Сейчас
  только в локальной сети; доступ через удалённый сервер отложен (спека,
  «Вне рамок»).
- **Четыре веб-страницы**: статус, настройки (счётчик, порт, облако), Wi-Fi,
  лог в реальном времени с байтами оптопорта (кольцевой буфер 16 КБ).
  Выбор типа счётчика не нужен.
- **Периодическая отправка в облако Waterius.** Перед каждой отправкой
  прошивка читает счётчик: энергию по каждому тарифу и сумму, время
  счётчика и версию его ПО.

### Архитектурные следствия

- **Serial-транспорт у S3 и C3 разный.** У C3 USB — только Serial/JTAG,
  хоста нет. Поэтому на C3 работает только доработанная головка на
  аппаратном UART. У S3 есть USB OTG: к нему можно подключить
  **недоработанную** головку как USB-хост к CP210x, или ту же
  доработанную на UART (см. `docs/05-alternatives.md`). Интерфейс
  транспорта в порте должен покрывать оба варианта.
- **Один оптопорт на двух потребителей.** Его делят опрос и прозрачный
  режим через `OptoBus`. Подключение клиента RFC 2217 сразу прерывает
  идущий опрос (до следующего цикла); после отключения порт свободен, а
  параметры порта выставляет себе каждый опрос при старте.

## Протокол НАРТИС (оптопорт)

«Нарцисс/Нарцис» — это **НАРТИС** (ООО «Завод НАРТИС», Череповец).
Здесь счётчик **НАРТИС-100.121RL**: 230 В, 5(60) А, класс точности 1
(тип так и прочитан со счётчика). В обозначении **`R` — радиомодуль RF ТРР
с внутренней антенной**, `L` — реле (RS-485 — `S`, GSM — `G`). У этого
исполнения из интерфейсов только оптопорт и радио.

Всё ниже, что помечено «проверено», подтверждено опросом живого счётчика
скриптом `tools/nartis_probe.py`; полный дамп кадров —
`docs/06-nartis-100-exchange.md`.

- Протокол — **СПОДЭС = DLMS/COSEM поверх HDLC** (ГОСТ Р 58940-2020,
  СТО 34.01-5.1-006). **Это не IEC 62056-21 mode C.** Пример из
  `docs/04-firmware.md` (`/?!` на 300 7E1) для НАРТИС не подходит.
- Формат оптопорта — **9600 8N1**, сразу, без согласования скорости (так
  подключается конфигуратор Nartis Tools; проверено, эха у головки нет).
  Резервный вариант по СТО —
  режим E: `/?!\r\n` на 300 7E1, затем ACK, затем HDLC 8N1 на скорости
  Z. Режим E не реализован (вне рамок спеки): прошивка сразу шлёт SNRM на 9600.
- **Серийный номер для оптопорта указывать не нужно.** Адрес сервера:
  logical 1, physical **16** у серии 100/300 (проверено; у серии И — 17), 2 байта.
  В кадре это `0x02 0x21` для 16 и `0x02 0x23` для 17. В РЭ на 100
  значение адреса не опубликовано, поэтому `NartisMeter` при `meterAddr = 0`
  перебирает 16, затем 17. Серийный номер читается после ассоциации из
  OBIS `0.0.96.1.0.255`; он нужен только для каналов RF433 и BLE.
- Клиент **32** (считыватель), адрес клиента в кадре — `0x41`. Клиент 16
  (публичный) не видит паспортные данные.
- **Заводские пароли у серии 100 и у серии И разные.** У НАРТИС-100 по РЭ:
  чтение — `111` (проверено), конфигурирование — `12345`; это и стоит по
  умолчанию.
  `00000001` — пароль И-серии. **После 5 неверных паролей счётчик
  блокирует интерфейсы на сутки**, поэтому пароль берётся только из
  настроек: никакого перебора в коде быть не должно.
- OBIS:
  - `1.0.1.8.0.255` — активная энергия импорт, сумма;
  - `1.0.1.8.1.255` … `1.0.1.8.4.255` — тарифы T1…T4 (объекты T5…T8
    тоже есть, у этого счётчика в них 0);
  - `0.0.1.0.0.255` — дата и время (класс 8, атрибут 2);
  - `0.0.96.1.2.255` — версия метрологического ПО (`255.06`) — её и
    считаем версией ПО счётчика;
  - `0.0.96.1.3.255` — **изготовитель** (`Zavod Nartis`), не версия ПО;
  - `0.0.96.1.8.255` — вероятно, версия коммуникационного ПО: 4 байта
    `01 15 05 06` (1.21.5.6), не проверено;
  - `0.0.96.1.1.255` — тип счётчика, строка в cp1251.

  У регистров класса 3 значение лежит в атрибуте 2, масштаб — в
  scaler_unit (атрибут 3). Проверено: энергия приходит как
  double-long-unsigned в Вт·ч со scaler 0, все строки и даты — как
  octet-string (`09`), а не visible-string или date-time. Счётчик
  разрешает block-transfer-with-get, max PDU 1000, max info field 256.
- Эталонная реализация — [latonita/esphome-dlms-cosem](https://github.com/latonita/esphome-dlms-cosem).
  НАРТИС И100-W112 в ней проверен на RS-485, по оптопорту она работает
  только на фиксированных 9600. Документация: РЭ И100 НРДЛ.411152.101РЭ,
  руководство Nartis Tools, СТО 34.01-5.1-006-2017 (ссылки перенести в
  `docs/sources.md`).

## Облако Waterius

Прошивка Waterius и бэкенд лежат рядом: `~/CODE/waterius/ESP8266`
(PlatformIO, ESP8266) и `~/CODE/waterius.site.back` (Django).

- Для электросчётчика подходит эндпоинт **`POST /api/source/iz/`**
  (`apps/source/api.py`, `IZSerializer` в `apps/source/serializers.py`),
  а не `/api/source/waterius/`, который рассчитан на импульсные каналы.
  Хост по умолчанию — `https://cloud.waterius.ru`. Устройство
  опознаётся по полю `key` в теле (4–40 символов). Waterius дополнительно
  шлёт заголовки `Waterius-Token` и `Waterius-Email`.
- Поля: `total`, `total1`…`total4`, `data_type`, `data_type1`…`4`,
  `sn` (≤15 символов), `fw` (версия прошивки ESP, ≤30), `chip_id`
  (int), `ip`, `rssi`, `company`, `place`, `mqtt_on`, `ha_on`.
  Коды `data_type`: 2 — электричество (сумма), 5 — день, 6 — ночь,
  7 — пик, 8 — полупик. Образец полного запроса — тест
  `test_iz_server_ekt5ce102m` в `apps/source/pytest/pytest_iz.py`.
- **Для времени и версии ПО счётчика полей нет.** `fw` — это версия
  прошивки ESP. Прошивка шлёт их дополнительными полями `meter_fw`,
  `meter_time`, `meter_read_at` вместе с кодом ошибки OTA `ota_error` —
  бэкенд их пока игнорирует.
- Успех — только HTTP 200. Из ответа прошивка разбирает только блок `ota`
  (OTA через сервер, как в waterius); выдачу его для `/api/source/iz/`
  владелец добавит в бэкенд отдельно.
- **Канала для прозрачного serial через сервер в бэкенде нет** (нет
  websocket, MQTT-брокера, прокси). Серверную часть придётся
  проектировать отдельно.
